FlipScope — Technical Audit

Prepared by Powerclub Global · 2026-08-18 · Source reviewed: flipscope_final_polished.html (single file, 366 lines) + live Supabase backend

Bottom line. FlipScope is a well-crafted single-file front-end prototype — clean UI, sensible information architecture, 18 feature screens, and a real Supabase sync layer whose Row-Level Security we verified is actually enforced. It is not yet a product: the "AI" is keyword matching, the "live forecast" is hardcoded, uploaded media is never persisted, and — most seriously — the same project reports three contradictory profit numbers ranging from −$5,250 to +$35,550. The foundation is genuinely good. The gap to a credible, sellable tool is a focused engineering pass, not a rebuild.

What it actually is

A standalone HTML/CSS/JS application. State lives in localStorage under one key (flipscope_worldclass_v1) with a seeded demo project (212 E Maple, Perry OK). An optional Supabase layer (loaded from CDN) signs a user in and pushes/pulls the project across ~14 tables. There is no build step, no framework, no server of its own — it runs by opening the file. That is a strength for a demo and a limitation for a product.

1 · The numbers don't agree CRITICAL

This is the most damaging issue for an investor/lender-facing tool. FlipScope's own marketing copy says financials are "always reconciled." They are not. The same seed project produces:

ScreenLabelValueHow it's computed
Command Center / SidebarProjected Profit+$26,000 (14.5% ROI)ARV − committed
Command Center → ForecastForecast Profit+$35,550 (21.0% ROI)hardcoded in seed; never recalculated
Deal UnderwritingNet Profit−$5,250 (−2.6% margin)full model incl. selling/holding/financing/contingency

The Deal Underwriting model is the only honest one — it includes the ~$14,350 selling cost, financing, holding and contingency — and it says this deal loses money and flags "REVIEW DEAL." Meanwhile the home screen the user lands on celebrates a $26K profit. Worse, the "Forecast Final Cost" of $169,450 is lower than the already-committed $179,000, which is logically impossible (a forecast of final cost can't be below money already committed).

Fix

  • Pick one profit engine — the Deal Underwriting model — and have every screen read from it. Delete ARV − committed as a "profit" (it's equity spread, label it as such).
  • Make forecast.profit/roi/finalCost computed outputs, not seed constants.
  • Add an invariant/test: forecastFinalCost ≥ committed and all screens show the same profit to the dollar.

2 · Stored XSS through innerHTML CRITICAL

Almost every render function builds HTML with template strings and assigns to innerHTML, interpolating fields the user (or a co-worker on a shared cloud project) controls — scope task names, vendor names, member names, punch titles, daily-log text, the walkthrough transcript, and prompt() inputs. None are escaped. Examples:

  • renderScope() → <input value="${s.task}"> and row cells
  • renderTeam() → member name/role/access
  • renderMaterials() → material name/vendor (pulled from Supabase)
  • saveDailyLog()/renderField(), addCalendarTask() via prompt()

A value like <img src=x onerror=...> saved in any of these fields executes when rendered. In single-user demo mode the blast radius is the user's own browser. But the whole selling point is shared projects (owner, PM, field crew, investor) syncing through Supabase — so a field user's malicious task name runs in the investor's session. This is a genuine stored-XSS vector the moment multi-user is real.

Fix

  • Add one esc() helper (& < > " ') and wrap every interpolated value, or switch to textContent/createElement for user data.
  • For attribute contexts (value="${...}") escape quotes too — currently resolveAction only escapes single quotes for its onclick, which is not enough.

3 · Open signup on the backend HIGH

The Supabase auth settings endpoint reports disable_signup: false. Anyone with the (public, embedded) anon key can create accounts against this project via the API, even though the app itself has no signup UI — only signInWithPassword. RLS is owner-scoped so a stranger's account sees only their own empty project (not a data breach), but it's an unnecessary abuse surface: spam accounts, auth-quota consumption, confirmation-email volume.

Fix

  • Set Disable signup in Supabase Auth, and provision users by invite; or gate signup behind an allowlist / server function.
  • Keep mailer_autoconfirm: false (already correct — good).
VERIFIED GOOD RLS is genuinely enforced. Non-destructive probes with the anon key: reads of projects/scope_items/materials/schedules return [] (filtered, not leaked); inserts into projects and materials were rejected with new row violates row-level security policy. No rows were created. The embedded sb_publishable_… key is a publishable key and is safe to ship because RLS is on. This is the single most important thing a Supabase app has to get right, and the colleague got it right.

4 · The "live" intelligence isn't live HIGH

Forecast, risk score, cashflow and the Copilot answers all read from static seed objects (S.forecast, S.cashflow, S.risks). Editing scope, awarding a bid, or approving a change order updates the basic metrics but never recomputes the forecast, risk score, or cash plan. The badges say "LIVE FORECAST" / "PROJECT AWARE." The Copilot is an if/else keyword matcher over those static numbers, and analyzeWalkthrough() ("Generate AI Scope") is likewise keyword matching over the transcript — no model call, no video understanding. That's fine for a prototype but must not be sold as AI.

Fix

  • Derive forecast/cashflow/risk from the actual scope+cost+schedule state, or clearly label them "Illustrative."
  • If real AI is the pitch, wire analyzeWalkthrough and Copilot to an actual model (Claude) server-side — never with keys in the client.

5 · Field media evaporates HIGH

fieldMedia() and the room/video uploads use URL.createObjectURL() and drop the element into the DOM. Nothing is uploaded to Supabase Storage. On reload every "timestamped project documentation" photo, the walkthrough video, and the designer room image are gone. For a product whose core promise is "proof before sign-off," verification evidence that doesn't persist is a foundational gap.

Fix

  • Upload media to Supabase Storage, store the object path/URL on the related row, render from storage. Add EXIF/time metadata for the "timestamped" claim.

6 · Access control has no depth MEDIUM

ownedProject() runs select * from projects order by created_at desc limit 1 with no owner filter — it trusts RLS entirely to scope the row. replaceRows() does delete … eq('project_id', id), again trusting RLS to stop cross-tenant deletes. Today RLS holds, so this is safe. But it's a single point of failure: one permissive policy edit, one migration that forgets a table, and this code silently serves or deletes another tenant's data. Defense-in-depth costs one line.

Fix

  • Add explicit .eq('owner_id', userId) to reads and a project-ownership check before replaceRows. Belt and suspenders with RLS, not instead of it.

7 · Scheduler & estimates are naive MEDIUM

  • autoScheduleFromScope() stacks every task end-to-end (cursor += full duration) — no parallel trades, no dependencies. Flooring waits for cabinets even though they're independent, inflating the timeline.
  • estimateScopeDays() is unit-blind: paint is qty × 3 days regardless of unit, so a paint line entered in SF instead of LS produces thousands of days.
  • awardBid() maps a bid to a cost code by substring (cat.includes(trade)): trade "Cabinets" never matches cost code "Kitchen," so the commitment silently isn't recorded.
  • commitCapture() adds items with status "AI Draft", which isn't one of the scope dropdown options — the select renders blank.
  • approveChange() appends a new cost row every click with no idempotency guard — double-clicking double-commits the change order.

8 · Hardcoded numbers on a data screen MEDIUM

Project Health shows "68 line items · 7 trades" and "34% of work verified complete"; the Reports page shows "Scope Completion 34%." The seed actually has 6 scope items across 6 trades and 0 verified. These are literal strings, not computed — they'll stay wrong on a real project and undermine trust the moment someone counts.

9 · One project, not a portfolio MEDIUM

localStorage uses a single fixed key and the cloud loader always pulls the latest project only. There's no project switcher, list, or creation flow in the UI. For a flipper running several deals — the obvious buyer — this is a hard ceiling. The DB schema supports multiple projects; the app doesn't.

10 · Accessibility & platform LOW

  • Icon-only buttons (☰, ×, •••, record) have no accessible name; the contenteditable transcript has no label.
  • Camera/mic and webkitSpeechRecognition need a secure context (https/localhost) and are Chrome-only — opening from file:// or Safari, capture silently degrades. The graceful "upload instead" fallback is good; document the browser requirement.

11 · Backend hygiene LOW

Read probes returned 200 [] for some tables but 401 permission denied for function owns_project for ~10 others (members, forecasts, actions, logs, changes, bids, warranties, closeout, punch, feed). The asymmetry means the anon role wasn't granted EXECUTE on owns_project uniformly. It fails closed (denies), so it's not a security hole — just an uneven migration worth tidying so behavior is consistent for legitimate authenticated users.
