2 · Phase 0 — Foundation

Everything else in the plan is built on top of this: the schema, the money model, and the pipeline that keeps environments honest.

2.1 Data model

Every table below organizations carries an org_id (directly or via its parent), which is what row-level security keys on. ledger_entries is the single source of budget/committed/actual figures — nothing else stores money.

2.2 Money model — the one rule that can't slip

All monetary values are stored as integer cents, never floats. Budget, committed, actual, profit and ROI for a project are derived from ledger_entries by one server-side function — the UI never computes totals independently. This is the fix for the single biggest class of bug in spreadsheet-based flip tracking (rounding drift, two screens disagreeing). It must be correct before Phase 1 or 2 build anything on top of it.

3 · Phase 1 — Trust, roles & evidence

This is what makes the numbers believable to an investor and the app safe to hand to a crew: who can do what, an unerasable history, and photos that prove the work happened.

3.1 Role permission matrix

Enforced as RLS policies in Postgres, not just UI hiding — a Field Crew token cannot read financial tables even via direct API calls.

3.2 Proof-chain media flow

Once written, a proof-chain record cannot be edited or deleted through the app — only appended to. This is what an investor read-only view is actually trusting.

4 · Phase 2 — Portfolio layer

This is what turns FlipScope from "one project's numbers" into "how is the whole portfolio doing" — the view that makes it worth running the business on.

4.1 Rollup & aggregation

Nothing here computes independently — every portfolio number is a re-aggregation of the same ledger_entries the project screen reads, so the two views can never disagree.
